# トラブルシューティング(Let's Blog VSCode拡張)

## まず最初に: ログを見る

不具合の原因のほとんどはログで判別できます。

1. 設定 `letsBlog.debugMode` を `true` にする
2. 「表示 > 出力」→ 出力先のドロップダウンから **「Let's Blog」** を選ぶ
3. 問題の操作をもう一度実行する

エラー通知の「**ログを表示**」ボタンからも同じパネルを開けます。

ログには各API呼び出しの `メソッド URL -> ステータス` が記録されます。
アクセストークン等、資格情報に相当するキーの値は `***` にマスクされるため、そのまま共有できます。

## 接続できない

### 「サーバー(...)へ接続できませんでした」

| 確認 | 対処 |
| --- | --- |
| サーバーが起動しているか | `docker compose ps` でリバースプロキシ(`lbs-reverse-proxy`)とAPIゲートウェイ(`lbs-gateway`)の状態を確認 |
| `letsBlog.serverUrl` が正しいか | 既定は `https://localhost`。ポート指定が必要な構成なら含める |
| 証明書エラーではないか | 下の「証明書のエラー」を参照 |

このメッセージは、まだどの下流サービスにも届いていない(リバースプロキシ/gatewayへの到達性の問題)
ことを意味します。個々のサービスのログを見る前に、この2つのコンテナを確認してください。

### 「担当サービス: ○○ (コンテナ: lbs-xxx)」を含むエラー(issue #585)

gateway までは到達したものの、転送先の下流サービスがエラーを返した(または応答しなかった)場合に
表示されます。サービス分割(Epic #551)により、`/api/**` のパスごとに担当するコンテナが異なります。

| 対処 |
| --- |
| メッセージ中の `docker logs lbs-xxx` でそのサービスのログを確認する |
| メッセージに相関ID(`X-Correlation-Id`)が含まれる場合、`docker compose logs \| grep <相関ID>` で gateway と下流サービスをまたいだ経路を追う |
| `docker compose ps` で該当コンテナが healthy かを確認する |

`APIエラー (502)` で先頭に「サーバーからの応答: …」が付く場合は、gateway は担当サービスへ到達済みで、
担当サービスの上流(ComfyUI などの外部サービス)が失敗しています。コンテナの起動確認より先に、
応答内容(例: ComfyUIのチェックポイント未配置)に沿って上流の状態を確認してください(issue #1082)。
応答本文が無い502のときだけ、担当サービスへ到達できなかったものとしてコンテナの起動を確認します。

どのパスがどのサービスへ振り分けられるかは `services/gateway/src/main/resources/application.yml` の
ルート表が決めます(拡張側の対応表は `src/downstreamServices.ts`)。

### 証明書のエラー(`DEPTH_ZERO_SELF_SIGNED_CERT`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE`)

TLS証明書の検証は**既定で有効**です(`letsBlog.allowInsecureTls: false`)。
自己署名証明書のローカル環境へ接続する場合は、次のいずれかが必要です。

1. **推奨**: `NODE_EXTRA_CA_CERTS=/path/to/certs/localhost.crt` を設定してVSCodeを起動する
2. OSの証明書ストアに `certs/localhost.crt` を登録する
3. `letsBlog.allowInsecureTls: true` にする
   — 中間者攻撃を検出できなくなります。信頼できるネットワーク上のローカル環境でのみ使用してください。

3を選んだ場合、リクエストのたびに警告がログへ出ます(意図せず有効なままになるのを防ぐため)。

**注意**: 上記1〜3はいずれも拡張ホスト(Node.js)からのAPI呼び出しにのみ有効。
draw.ioエディタ(ダイアグラムの新規作成・編集)を使う場合は、下の
「draw.ioエディタが真っ白」を参照。

### 「応答が ... 秒以内に返りませんでした」

AI生成や画像生成は数十秒かかることがあります。
`letsBlog.requestTimeoutMs`(既定 120000)を延ばしてください。

## 認証・権限

### 既存ユーザーへの移行案内(issue #565: Device Authorization Grantへの移行)

拡張の認証方式が、メールアドレス/パスワードでのログイン(旧`letsBlog.setApiKey`によるAPIキー手入力を
含む)から、**Device Authorization Grant**(Keycloakへブラウザ経由で承認する方式)へ変わりました。

- `letsBlog.setApiKey` コマンドは削除されました。以前保存していたAPIキーはもう使われません。
- アップデート後、初回のAPI呼び出し時に未ログイン扱いになります。**「Let's Blog: Login」を実行して
  再ログインしてください**(表示されたコードをブラウザの画面に入力して承認するだけで完了します)。
- 以前保存されていたAPIキー/Actorの情報は、次にログインすると新しいアクセストークン/リフレッシュ
  トークンで上書きされます。手動で削除する必要はありません。

| 症状 | 原因と対処 |
| --- | --- |
| `APIエラー (401)` | アクセストークンが無効。通常は自動リフレッシュされるため、発生する場合はリフレッシュも失敗している(リフレッシュトークンの失効等)。「Let's Blog: Login」で再ログイン |
| `APIエラー (403)` | 対象プロジェクトのメンバーでない。管理者に確認 |
| 「保存されたログイン情報を読み込めませんでした」 | SecretStorageの値が壊れていたため破棄されました。再ログインしてください |
| 「ログインしていません」 | 未ログイン(トークン未設定)。「Let's Blog: Login」を実行 |
| 「ログインの有効期限が切れました」 | リフレッシュトークンが失効/取り消された。「Let's Blog: Login」で再ログイン |
| ログイン実行後、ブラウザが開かない | 既定ブラウザの起動に失敗した可能性があります。通知に表示されるコードと検証URLを控え、手動でブラウザから開いてください |
| コード入力後もログインが完了しない | Keycloak側で承認が完了しているか確認してください。認可コードには有効期限があり、切れた場合は「認可コードの有効期限が切れました」と表示されるので「Let's Blog: Login」からやり直してください |

## 投稿まわり

| 症状 | 原因と対処 |
| --- | --- |
| 「front matterに 'title' がありません」 | `article.md` の front matter に `title` を追加 |
| 「プロジェクトが未選択です」 | front matterに `project_id` を書くか、「Select Project」を実行 |
| 「投稿先サイトが紐づいていません」 | 管理画面でプロジェクトにサイトを紐付ける |
| 画像が投稿に含まれない | 「以下の画像ファイルが見つからないため…」の警告を確認。`article.md` からの相対パスで `assets/` 配下に置かれている必要があります |
| 更新のつもりが新規投稿になる | front matterの `wp_post_ids` にそのサイトキーの記録があるか確認。サイトごとに投稿IDを持つ仕様です |
| `APIエラー (413)` | 同梱画像が大きすぎる。枚数やサイズを減らす |

### 公開予定日時が効かない

`publish_scheduled_at` は**本番(live)サイトへの投稿でのみ有効**です。
ローカル/テスト環境では動作確認を優先して無視され、通常投稿になります(サーバーのログに残ります)。

指定はタイムゾーンを含むISO 8601形式である必要があります。

```yaml
publish_scheduled_at: "2026-12-25T09:00:00Z"       # OK
publish_scheduled_at: "2026-12-25T18:00:00+09:00"  # OK
publish_scheduled_at: "2026-12-25T09:00:00"        # NG(タイムゾーンなし)
```

「Let's Blog: Schedule Publication」を使うと、日付と時刻を選ぶだけで正しい形式が書き込まれます。

| --- | --- |

## Webviewパネル

| 症状 | 原因と対処 |
| --- | --- |
| パネルが開かない/真っ白 | 開発者ツール(「ヘルプ > 開発者ツールの切り替え」)のConsoleを確認。CSP違反が出ていないか見る |
| ボタンが押せないまま | 処理が実行中です。Escapeキーまたは「キャンセル」で中断できます |
| 閉じたパネルが再度開かない | 通常は起こりません(生存管理は`showSingletonPanel`が一元管理)。発生した場合はウィンドウの再読み込みで回復します |

### draw.ioエディタが真っ白(「Add New Diagram」「Edit Diagram」を開いても何も表示されない)

draw.ioエディタは他のWebviewパネルと異なり、`https://localhost/drawio/` をVSCode Webview内の
iframeとしてChromiumのレンダラープロセスが直接読み込む。ローカル環境の `https://localhost` は
自己署名証明書を使用しているため、証明書がブラウザ(Chromium)側で信頼されていないと
iframeの読み込みが証明書エラーでブロックされ、エラー表示もなく画面が白紙のままになる。

上の「証明書のエラー」節にある `letsBlog.allowInsecureTls` や `NODE_EXTRA_CA_CERTS` は
拡張ホスト(Node.js)側の対策であり、**この症状には効かない**。OS/ブラウザの証明書ストアへの
登録が必要。手順は [docs/setup.md](../docs/setup.md) の「7. VSCode拡張の設定」を参照
(Linuxでは `certutil` によるNSSデータベースへの登録が必要)。

登録後はVSCodeを完全に再起動すること(ウィンドウの再読み込みのみでは反映されないことがある)。

## 「サーバーの応答が想定した形式ではありませんでした」

APIサーバーと拡張のバージョンが噛み合っていない可能性があります。

1. `letsBlog.debugMode` を有効にして再実行する
2. ログの `レスポンス検証に失敗しました` の行を見る。どのフィールドがどう不一致かが出ます
3. サーバー側のAPI仕様が変わっている場合は、`src/schemas.ts` の該当スキーマを更新する

## 開発時

| 症状 | 対処 |
| --- | --- |
| `npm run compile` が失敗 | 型エラーの内容を確認。`npx tsc --noEmit -p ./ --noUnusedLocals` で未使用の変数も検出できます |
| テストが失敗する | `npx jest --coverage` を実行。`frontMatter` / `headingContext` / `config` はカバレッジ100%が閾値です |
| テストで `Cannot find module 'vscode'` | `jest.config.js` の `moduleNameMapper` が `src/__mocks__/vscode.ts` へ向いているか確認 |
| Webviewの変更が反映されない | `webviews/` の資材はビルド不要ですが、パネルを開き直す必要があります |
