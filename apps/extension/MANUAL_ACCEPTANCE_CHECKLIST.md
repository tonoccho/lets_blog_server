# VSCode拡張 手動受け入れチェックリスト

リリース前に**人が VSCode 上で確認する項目**の一覧(issue #942 / AT-16)。

拡張の検証は二層で行う(docs/ACCEPTANCE_CRITERIA.md §2.14、docs/ACCEPTANCE_TESTING.md)。

| 層 | 何を検証するか | 置き場所 |
| --- | --- | --- |
| Layer 1(APIレベル受け入れテスト) | 拡張自身の `apiClient` / `httpClient` が呼ぶサーバー契約 | `apps/extension/e2e/features/**/*.feature` |
| Layer 2(単体テスト) | front matter・見出し文脈・Markdown抽出・キャッシュ・パネルの状態遷移などの純ロジック | `apps/extension/src/__tests__/**` |
| **このチェックリスト** | **VSCode の UI 操作そのもの**(コマンドパレット、エディタへの挿入位置、Webview のクリック、キーバインド) | この文書 |

## なぜ自動化しないのか

実 VSCode インスタンスを起動する UI テスト(`@vscode/test-electron` 等)は
**AT-16 のスコープ外**である(#942 の Out of Scope。導入するなら別 Issue)。
拡張ホストが要る操作——コマンドパレットからの起動、エディタの選択範囲、
クリップボード、Webview の DOM 操作、draw.io の iframe——は、
Layer 1 / Layer 2 のどちらからも観測できない。
**観測できないものを「検証済」と書かない**ために、ここへ明示的に書き出す。

## 使い方

- リリース(拡張の `.vsix` 配布、AT-14 / #940)の前に、この一覧を上から実行する。
- 環境は開発スタック(`https://localhost`)で足りる。`letsBlog.allowInsecureTls` は `true`。
- 失敗したら Issue を立てる。チェックリストに「既知の不具合」を書き足して回避しない。

## 1. 前提の準備

- [ ] `letsBlog.serverUrl` / `letsBlog.allowInsecureTls` を設定した VSCode で拡張を起動できる
- [ ] 出力パネル「Let's Blog」が作られ、`letsBlog.debugMode` を有効にするとログが出る

## 2. ログインと設定(AC-EXT-001 / 014)

- [ ] `Let's Blog: Login` を実行すると user code が表示され、ブラウザが承認画面で開く
- [ ] 承認後に「ログインしました」と表示され、ロール名が読める文言で出る
- [ ] 承認せずに放置した場合、待機中であることが分かる表示のまま失敗しない
- [ ] `Let's Blog: AIプロバイダーを切り替える` の選択肢(既定/OLLAMA/OPENAI/CLAUDE)が出て、選ぶと設定へ保存される

> トークンの保存・自動更新・証明書検証・接続失敗時のメッセージは Layer 1
> (`e2e/features/auth/`)で自動検証済み。ここで見るのは**画面表示だけ**。

### 2.1 セッションの寿命とサーバー瞬断(issue #1098)

`offline_access` を要求した結果 Keycloak が実際に offline token を発行するかは、
**拡張のコード側からは観測できない**(検証対象が Keycloak の応答そのものであり、
単体テストではモックした応答しか見られない)。ローカルスタック(`https://localhost`)に対する
手動確認としてここに置く。

- [ ] ログイン直後、`letsBlog.debugMode` を有効にした状態で保存された `refresh_token` の
      JWT ペイロードをデコードし、`typ` クレームが `Offline` であることを確認する
      (ペイロードは `echo '<refresh_token の2番目のセグメント>' | base64 -d` で読める)
- [ ] ログインから **30分以上**(realm の `ssoSessionIdleTimeout` = 1800 秒を超過)
      拡張のコマンドを一切実行せずに放置した後、`Let's Blog: Select Project` を実行すると
      再ログインを求められずに成功する
- [ ] `docker compose restart keycloak` の実行中(Keycloak が応答しない間)に
      `Let's Blog: Select Project` を実行すると、「一時的な失敗」である旨のメッセージが出て
      **再ログインは案内されない**
- [ ] 上記の直後、Keycloak が復帰してから同じコマンドを再実行すると、
      再ログインなしで成功する(`letsBlog.tokens` が消えていない)

- [ ] 1つのステップだけがサーバエラーになる状況(例: 該当ステップのAI呼び出しを失敗させる)で実行すると、
      他のステップの指摘は表示され、失敗したステップ名を含む警告が出る。全ステップが失敗したときはエラーになり、既存の表示は残る

      (**スタブ環境では再現できない。#1004。実プロバイダーでのみ確認可能**)
- [ ] ログアウトした状態で `校正チェックを今すぐ実行` を実行すると、「Let's Blog: Login」を促すエラーが表示され、AIサーバーへリクエストが出ない
- [ ] 設定に `letsBlog.proofreadEnabled` / `letsBlog.proofreadDebounceMs` が残っていても拡張は通常どおり起動し、
      設定画面には廃止の注記が表示され、有効にしても自動実行されない
- [ ] front matter の不正(過去日時の `publish_scheduled_at` / 不正な `status` / 存在しないカテゴリ)は、
      編集の都度(約0.5秒のデバウンス後)に赤い波線で表示され、QuickFix が使える(本文のアンダーラインとは別系統)
- [ ] 生成中に「キャンセル」を押すと処理が中断され、エラー通知にならない

### 5.1 指摘チェックリスト(issue #1216)

対応状態のワークスペース状態(`context.workspaceState`)への保存・復元と、レビュー再実行時の
同一性判定(ステップキー・引用文・指摘内容)はjest単体テスト(`src/__tests__/reviewChecklistLogic.test.ts` /
`reviewChecklistStore.test.ts` / `reviewChecklistPanel.test.ts`)とWebview境界のDOMテスト
(`reviewChecklistWebview.test.ts`)で検証済み。**VSCodeの実際の再起動**と**実際のクリック操作**は
自動化できないため、ここで確認する。

- [ ] `校正チェックを今すぐ実行` の後に `Let's Blog: 指摘チェックリストを表示` を実行すると、
      別タブに指摘がステップごと(日本語チェック→校正チェック→校閲→読者視点でのチェック→文体チェックの順)に
      まとまったチェックリストとして表示される(AC1)
- [ ] 各項目の対応状態を「未対応」「修正済み」「スキップ」の間で切り替えると、その項目の見た目
      (枠の色)が切り替わる(AC2)
- [ ] 対応状態を変えた後、VSCodeを再起動して同じ記事を開き `Let's Blog: 指摘チェックリストを表示` を
      実行すると、変更前と同じ対応状態が復元されている(AC3)
- [ ] 本文に、既存の指摘の引用文より前の位置へ加筆したうえで `校正チェックを今すぐ実行` を再実行すると、
      その指摘は(本文中の位置がずれても)チェックリスト上で対応状態を保ったままである(AC4)
- [ ] 指摘の引用文を含む一文を本文から削除して再実行すると、その項目がチェックリストから消える
      (「該当箇所なし」としては残らない)(AC5)

### 5.1.1 校閲ステップのスキップの表示(issue #1545)

スキップ情報の記録・置き換え・旧形式の状態の読み込みはjest単体テスト(`reviewChecklistLogic.test.ts` /
`reviewChecklistStore.test.ts` / `reviewChecklistPanel.test.ts`)、描画(`textContent`のみ・指摘グループとの
区別)は`reviewChecklistWebview.test.ts`で検証済み。**実機での見た目**と**VSCodeの実際の再起動**は
自動化できないため、ここで確認する。スキップはサーバが理由つきで実行を見送ったステップで、利用者が項目に付ける
対応状態の「スキップ」とは別物である。

- [ ] サーバがあるステップをスキップする条件の記事(例: そのステップの対象にならない短い本文)で
      `校正チェックを今すぐ実行` の後に `Let's Blog: 指摘チェックリストを表示` を実行すると、
      「校閲が実行されなかったステップ」の欄に、そのステップ名とスキップ理由が表示される
- [ ] 同じパネルで、実行されて指摘0件だったステップは「校閲が実行されなかったステップ」の欄に
      現れない(スキップと指摘0件が見分けられる)
- [ ] VSCodeを再起動して同じ記事に対し `Let's Blog: 指摘チェックリストを表示` を実行すると、
      スキップの表示が復元されている
- [ ] スキップの条件を外して(本文を加筆するなど)`校正チェックを今すぐ実行` を再実行し、
      スキップが無くなると、「校閲が実行されなかったステップ」の欄が消える
- [ ] 指摘の項目の対応状態の選択肢「スキップ」は従来どおり使え、上記の欄とは別に表示される

### 5.2 指摘チェックリストからのジャンプ・件数・空状態(issue #1225)

本文からの探索(front matterを除く最初の一致)と未対応件数の算出はjest単体テスト
(`reviewChecklistLogic.test.ts`)、Webview境界のメッセージと表示は`reviewChecklistPanel.test.ts` /
`reviewChecklistWebview.test.ts`で検証済み。**実際のクリック操作とエディタ上のカーソル移動・表示位置**は
自動化できないため、ここで確認する。

- [ ] 指摘のある記事で `Let's Blog: 指摘チェックリストを表示` を実行すると、一覧の上部に「未対応: N件」が表示される(AC3)
- [ ] 項目の引用文(等幅フォントの部分)をクリックすると、記事のエディタが前面に出て、本文中の引用文が選択され、
      その行が画面内に表示される。記事のエディタを閉じてからクリックしても、記事が開いてから移動する(AC1)
- [ ] 同じ文字列が本文中に複数ある項目では、最初の一致箇所へ移動する(AC1)
- [ ] 指摘を取得した後、本文の先頭付近へ数行加筆してから項目をクリックすると、加筆でずれた後の位置へ移動する(AC1)
- [ ] 本文から引用文を削除(または書き換え)してから、その項目をクリックすると、チェックリストに
      「本文に見つかりません」と表示され、エディタのカーソル位置は変わらない。別の項目をクリックすると表示が消える(AC2)
- [ ] 項目の対応状態を「修正済み」「スキップ」へ変えると、「未対応: N件」の数がその場で減り、「未対応」へ戻すと増える(AC4)
- [ ] 指摘が0件になるレビュー結果を記録した記事(指摘が出ない短い本文で `校正チェックを今すぐ実行`)で
      チェックリストを表示すると、白紙ではなく「指摘はありません」と表示される。
      レビューを一度も実行していない記事では、この表示も件数も出ない(AC5)

### 8.1 実サイトの署名付きURLでの表示(issue #1562)

自動化しているのは署名付きURLの取得と導入案内の判定(`e2e/features/articles/preview-signed-url.feature`)まで。
パネルの表示そのものはここで確認する。旧方式(骨格・CSS取得)のプレビューの削除は #1564 の範囲で、
サイトが紐づいていない記事だけ旧方式のまま表示される。

## 11. 差し戻しの通知(issue #1347)

自動テストはロジックのみ。通知の見え方・コマンド・設定変更の反映はここで確認する。

- [ ] 自分が提出した記事が差し戻されると、VSCode に警告通知が出て、記事のスラッグ(タイトルはサーバー応答に無い)と指摘事項が読める
- [ ] 同じ差し戻しは、次の確認以降(コマンドの再実行を含む)で通知が繰り返されない
- [ ] コマンドパレットの「Let's Blog: 差し戻しを今すぐ確認」で、間隔を待たずに確認される
- [ ] 新たな差し戻しが無いとき、手動確認で「新たな差し戻しはありません。」と表示される
- [ ] ログアウト中に手動確認すると「ログインしていないため確認できません…」と表示される(エラー通知にはならない)
- [ ] プロジェクト未選択で手動確認すると「プロジェクトが未選択のため確認できません…」と表示される
- [ ] ログアウト中・プロジェクト未選択のまま起動・待機しても、通知もエラー通知も出ない
- [ ] `letsBlog.rejectionPollIntervalMs` を変更すると、VSCode を再起動せずに新しい間隔で確認される(10000 未満は 10000 として扱われる)

## 12. 差し戻し通知からの編集と再提出(issue #1348)

自動テストはブランチ切り替え・開くパス・指摘事項の保持まで。通知ボタン・出力チャネル・情報メッセージはここで確認する。

- [ ] 差し戻しの通知に「編集」ボタンがあり、選ぶと記事のブランチへ切り替わって `article.md` が通常のテキストエディタで開く(専用の WebView は開かない)
- [ ] 出力チャネル「Let's Blog: 指摘事項」に指摘事項が表示され、情報メッセージに「再提出」ボタンが出る
- [ ] 編集中に「Let's Blog: 指摘事項を表示」で、指摘事項をもう一度表示できる
- [ ] 「再提出」(または「Let's Blog: 再提出」)で、記事ディレクトリの変更がコミット・push され、サイト管理者の画面でレビュー状態が「提出済み」へ戻る
- [ ] 記事のブランチが無いワークスペースで「編集」を選ぶと、その旨が表示され、ブランチもエディタも変わらない
- [ ] 未コミットの変更がある状態で「編集」を選ぶと、切り替わらずに理由が表示される

## 自動化できていない理由の内訳

| 項目 | 理由 |
| --- | --- |
| コマンドパレットからの起動 | 拡張ホストが必要(#942 Out of Scope) |
| エディタへの挿入位置・選択範囲 | `vscode.TextEditor` の実体が必要 |
| Webview のクリック・フォーム操作 | Webview の DOM は拡張ホスト内にしか存在しない |
| draw.io / プレビューの iframe | 外部エディタの描画結果 |
| クリップボード・キーバインド | VSCode の入力系 |
| 通知・進捗・クイックピックの見え方 | UI そのもの |

自動化されている範囲は `apps/extension/e2e/README.md` を参照。
