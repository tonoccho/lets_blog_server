# 記事レビューワークフロー

GitHub Issue での記事計画から、Pull Request(PR)によるレビュー、本番公開、差し戻しと再提出までの流れを説明する文書です。
執筆者・サイト管理者・運用者が、コードを読まずに全体像と前提を掴むためのものです。

- 設計の一次情報は Epic #1333 とその子 Issue。この文書はその確定事項を、利用者向けにまとめ直したものです。
- 環境構築の手順は [GETTING_STARTED.md](GETTING_STARTED.md)、受け入れテストの書き方・実行方法は
  [ACCEPTANCE_TESTING.md](ACCEPTANCE_TESTING.md) を参照してください。ここでは繰り返しません。
- 拡張の内部構成は [apps/extension/ARCHITECTURE.md](../apps/extension/ARCHITECTURE.md) を参照してください。

---

## 1. 登場人物と責務の境界

| 担当 | 誰か | 主にやること |
| --- | --- | --- |
| 執筆者 | 記事を書く人 | 拡張で記事を選び、執筆し、提出・再提出する |
| サイト管理者 | 公開前に記事を確認する人 | Web 管理画面で PR を選び、レビュー・レビュー完了・差し戻しを行う |
| サーバ | publishing-service(`article-review`) | GitHub API 呼び出し(PR 作成・取得・コメント・マージ)、テスト/本番環境への投稿、レビュー状態の記録 |
| 拡張 | VSCode 拡張 | ローカル git 操作(ブランチ作成・コミット・push)、記事の編集、差し戻し通知の受け取り |

境界の原則は次の 1 行です。

> **ローカル git 操作は拡張が行い、GitHub API 呼び出しはサーバが行う。**

拡張は GitHub のトークンを持ちません。push の資格情報は後述のとおり利用者のローカル git 設定に委ねます。

## 2. 記事リポジトリの前提

| 項目 | 規約 |
| --- | --- |
| ワークスペース | **利用者が用意した clone** を VSCode のワークスペースとして開く。拡張は clone を作成・管理しない |
| 記事の置き場所 | ワークスペース直下の `articles/<slug>/{article.md,assets/}`(詳細は拡張の ARCHITECTURE.md) |
| 既定ブランチ | ブランチの起点。拡張は `origin` の既定ブランチ(`main` / `master` / `develop` の順に、存在するもの)の最新から切る。PR のマージ先もリポジトリの既定ブランチ |
| ブランチ名 | `article/<issueNumber>-<slug>`(例: `article/42-first-post`)。Issue 番号とスラッグから決まる |
| 1 PR = 1 記事 | 記事ディレクトリを 2 つ以上含む PR はエラー(サーバが 409 で拒否する) |
| リモート | push 先は `origin` |
| プロジェクト側の設定 | プロジェクトに GitHub リポジトリ(`owner/repo`)が紐付いていること。未設定だとサーバが 409 を返す |

## 3. GitHub トークン

### 3.1 必要な権限

PR を扱うため、従来の Issues スコープだけでは足りません。Fine-grained personal access token では
次の 3 つを付けてください。

| 権限 | レベル | 使われる操作 |
| --- | --- | --- |
| Issues | Read and write | 記事計画(Issue)の取得・登録・アサイン |
| Pull requests | Read and write | PR の作成・一覧・取得・コメント・マージ |
| Contents | Read and write | PR の head にある記事(`article.md`・assets)の取得、マージ後のブランチ削除 |

対象リポジトリは記事リポジトリ(プロジェクトに紐付けたもの)に絞ってください。

### 3.2 プロジェクト共通トークンと個人トークン

トークンの置き場所は 2 通りあり、**同じ権限(上表の 3 つ)** が必要です。

| 種類 | 設定場所 | 使われるとき |
| --- | --- | --- |
| プロジェクト共通トークン | プロジェクト詳細ページ | 設定されていれば常にこちらが使われる |
| 個人トークン | 操作した人のユーザー設定 | 共通トークンが無いときだけ、操作者本人のものが使われる |

サーバの GitHub API 呼び出し(PR 作成・コメント・マージ・記事の取得)は、既存の `githubAccess` の解決順に従います
(`ProjectInternalController` の `GET /api/internal/project/projects/{projectId}/github-access`)。

1. プロジェクトに GitHub リポジトリが紐付いていなければ 409(設定を促す文面)。
2. **プロジェクト共通トークンがあればそれを使う**(共通トークン優先)。
3. 無ければ、操作者個人のトークンを使う。それも無ければ 409(「ユーザーの GitHub トークンが設定されていません」)。

### 3.3 共通トークン使用時の見え方

- 共通トークンが設定されていると、GitHub 上の **PR 作成者・コメント投稿者は全員同じアカウント**(トークン所有者)になります。
  GitHub の画面だけでは、誰が提出・差し戻したかは分かりません。
- 提出者は Let's Blog 側の `article_reviews.submitted_by_user_id`(#1339)に記録されます。差し戻しの宛先もこの値で決まります
  (GitHub の assignee は使いません)。差し戻したサイト管理者は `rejected_by_user_id` に残り、PR コメントの本文にも書かれます。
- 個人トークンが使われた場合は、その人の GitHub アカウントが PR 作成者になります。

### 3.4 push の資格情報(拡張はトークンを持たない)

ブランチの push は、拡張が **利用者のローカル git 設定**(credential helper / SSH 鍵)を使って行います(#1342)。
拡張は GitHub のトークンを保存せず、サーバから受け取ることもありません。
そのため、執筆者は自分の clone で `git push` できる状態にしておく必要があります。
トークンの Contents 権限は、サーバ側の記事取得などのためのもので、push のためのものではありません。

## 4. 記事作成ワークフロー(要件 1〜12)

番号は Epic #1333 の利用者要求の番号です。「状態」は `article_reviews.state`
(`SUBMITTED` → `IN_REVIEW` → `PUBLISHED`、差し戻しは `CHANGES_REQUESTED`)の値です。

| # | ステップ | 担当 | 発生する副作用 |
| --- | --- | --- | --- |
| 1 | GitHub Issue に記事計画を登録する | サイト管理者(サーバ経由) | GitHub に Issue が作られる(既存機能) |
| 2 | 拡張で Issue を選ぶ | 執筆者(拡張) | サーバ経由で Issue 一覧を取得。副作用なし |
| 3 | ブランチを切り、雛形をコミットする | 執筆者の操作を受けて拡張 | ローカルに `article/<issueNumber>-<slug>` ブランチと雛形コミットができる。未コミットの変更があると中断する |
| 4 | ローカル環境へ投稿しながら執筆する | 執筆者(拡張→サーバ) | ローカル環境の CMS に記事が作られる(既存機能。テスト・本番へは影響しない) |
| 5 | 「記事の提出」を選ぶ | 執筆者(拡張) | 記事のコミットと `origin` への push(利用者の git 設定で認証)。記事用ブランチ以外では実行できない |
| 6 | PR を作成する | サーバ | 既定ブランチ宛の PR が作られ、`article_reviews` に提出者つきで記録される(状態 `SUBMITTED`)。同じ head に開いた PR があれば新規作成せずそれを返す |
| 7 | Web の PR 一覧から 1 件選び「レビュー」を押す | サイト管理者 | 開いている PR の一覧を GitHub から取得。選んだ PR の記事(front matter・本文・assets)を head から読む |
| 8 | テスト環境へ投稿する | サーバ | プロジェクトのテスト環境のサイトへ **即公開** で記事が投稿される(同じスラッグは更新なので重複しない)。状態が `IN_REVIEW` になり、投稿 URL が記録される。失敗時は状態が進まず、アップロード済みの画像は巻き戻さずに残る |
| 9 | テスト環境で記事を確認する | サイト管理者 | 副作用なし(確認先 URL が画面に出る) |
| 10, 11 | 「レビュー完了」を押す | サイト管理者 | 本番環境へ記事が登録される。公開状態は **front matter の `status` を尊重**(既定 `draft`、`publish_scheduled_at` があれば予約投稿)。拡張から本番へ投稿した場合と同じ規則 |
| 12 | PR をマージし、ブランチを削除する | サーバ | PR がマージされ、head ブランチが削除される。状態が `PUBLISHED` になる |

注意:

- 要件 1 と 2 と 4 は既存機能です。要件 3・5・6・7・8 は #1335・#1342・#1339・#1337/#1340・#1341 で、10〜12 は #1343・#1346 で扱います。
  実装の進み具合は Epic #1333 の子 Issue の状態が一次情報です。
- レビュー中に既定ブランチが進んで PR がコンフリクトした場合の自動解決は、このワークフローの対象外です。

## 5. 差し戻しワークフロー(10'〜14')

サイト管理者がテスト環境で確認して問題を見つけたときの流れです。

| # | ステップ | 担当 | 発生する副作用 |
| --- | --- | --- | --- |
| 10' | 「記事差し戻し」を選び、指摘事項を書く | サイト管理者 | 指摘事項が **PR のコメント** として投稿される(本文に差し戻した Let's Blog ユーザーが入る)。状態が `CHANGES_REQUESTED` になり、差し戻した人・日時・コメント ID が記録される。指摘が空だとコメントも状態変更も行われない。レビュー中でない PR は差し戻せない(409) |
| 11' | 提出者(担当者)へ通知する | 拡張 | 拡張が `my-reviews` を **ポーリング**(既定 5 分間隔)し、自分の提出分が差し戻されていれば VSCode に通知する。サーバに通知基盤は作らない。VSCode を閉じている間の差し戻しは、次回起動時にまとめて通知する |
| 12' | 通知から記事を開いて編集する | 執筆者(拡張) | ローカルの記事ファイルを編集する。指摘本文は PR コメントが正で、サーバは本文を複製して持たない |
| 13' | 「再提出」する | 執筆者(拡張→サーバ) | 修正をコミットして同じブランチへ push(利用者の git 設定で認証)。サーバは同じ head の既存 PR を返し、状態を `SUBMITTED` へ戻す |
| 14' | 手順 7 へ戻る | サイト管理者 | 以降は記事作成ワークフローの 7 から繰り返す。手順 8 は同じスラッグの投稿を更新する |

## 6. 状態の遷移

```
SUBMITTED ──レビュー(7,8)──▶ IN_REVIEW ──レビュー完了(10〜12)──▶ PUBLISHED
    ▲                           │
    │                           └──記事差し戻し(10')──▶ CHANGES_REQUESTED
    └────────────再提出(13')──────────────────────────────────┘
```

状態は `lbs_publishing` スキーマの `article_reviews` テーブル 1 枚で持ちます。GitHub のラベルだけで持たないのは、
差し戻しの宛先となる Let's Blog ユーザー ID を GitHub 側に置けないためです。
