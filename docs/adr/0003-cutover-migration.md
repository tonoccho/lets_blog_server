# ADR-0003: 旧認証機構は並行運用せず一括で切り替える

## Status

Accepted

## Context

[ADR-0002](0002-keycloak-oidc.md) により認証基盤を Keycloak (OIDC) へ移行することを
決定した。移行方式としては、新旧の認証機構をしばらく並行稼働させながら段階的に
切り替える方式と、あるタイミングで一括切り替えを行う方式が考えられる。

現行の `X-API-Key` / `X-Actor-*` ヘッダ方式・独自TOTP・独自パスワードリセットは、
[ADR-0002](0002-keycloak-oidc.md) の Context に記載した通りなりすましを許す構造的欠陥を
抱えている。この欠陥のある機構を新機構と並行運用する期間を設けることは、
脆弱性のあるログイン経路を延命させることを意味する。

## Decision

新旧認証機構の並行運用は行わず、Keycloak (OIDC) への一括切り替え(カットオーバー)を行う。
`X-API-Key` / `X-Actor-*` ヘッダ・独自TOTP・独自パスワードリセットは、カットオーバー完了後に
撤去する。

カットオーバーの安全性を担保するため、カットオーバー手順とロールバック方針を事前に
確定させ（Issue #591 [E5]）、その完了後に旧認証機構の撤去（Issue #566 [B8]）に着手する。

## Consequences

**利点**

- 脆弱性のある旧認証機構を並行運用する期間が発生せず、なりすましリスクの露出期間を
  最小化できる
- 新旧2系統の認証ロジックを同時にメンテナンスするコード的負債が発生しない
- 認可ロジックが単一の仕組み(JWTクレーム)に統一され、実装・レビューが単純になる

**欠点・トレードオフ**

- 切り替え当日に問題が発生した場合の影響範囲が大きく、ロールバック手順の事前整備が
  必須になる（Issue #591 で対応）
- 全クライアント(Web/VSCode拡張/サービス間通信)を同一タイミングで切り替える必要があり、
  移行当日の作業調整コストが高い

## Alternatives considered

**段階移行（新旧並行運用、却下）**

機能・ユーザー単位で段階的にKeycloak認証へ移行し、一定期間は新旧両方の認証経路を
稼働させる案。切り替え当日の影響範囲は小さくできるが、なりすましを許す脆弱な旧経路が
移行完了まで生き続けてしまい、[ADR-0002](0002-keycloak-oidc.md) で解決しようとしている
セキュリティ課題への対応が遅延する。また新旧2系統の認可ロジックを一時的に共存させる
実装が必要になり、実装・テストの複雑性がかえって増す。移行期間中に生じるバグの調査対象が
新旧どちらの経路かの切り分けコストも発生するため、一括切り替えの方が総合的にリスクが
低いと判断した。
