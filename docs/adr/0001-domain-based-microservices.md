# ADR-0001: ドメイン単位のフルマイクロサービス分割を採用する

## Status

Accepted

## Context

`api` は494ファイル・29,149行の単一 Spring Boot アプリケーションに、認証・プロジェクト管理・
記事コンテンツ・画像生成・図表レンダリング・WordPress発行・GA/AdSense分析・バックアップ・
VSCode拡張ビルド配布までが同居している。

デプロイ単位が1つしかないため、障害境界も1つしかない。たとえば画像生成(ComfyUI連携)の不具合が
記事投稿やユーザー管理といった無関係な機能の可用性にも影響する。また単一アプリのため、
ドメインごとに異なるスケーリング要件（例: 画像生成はGPU律速、認証は低レイテンシ要求）を
個別に満たすこともできない。

コードベースの肥大化により、変更の影響範囲の把握やテストのコストも増加し続けている。

## Decision

ドメイン単位でサービスを完全に分割する（フルマイクロサービス化）。各サービスは独立した
デプロイ単位・独立したデータストア（スキーマ）を持つ。

分割対象は以下の通り。

- `api-gateway` — JWT検証・ルーティング・レート制限・相関ID付与
- `identity-service` — 認証・ユーザー管理
- `project-service` — サイト/プロジェクト管理
- `content-service` — 記事コンテンツ
- `media-service` — 画像生成(ComfyUI連携)
- `ai-service` — AI執筆支援
- `publishing-service` — WordPress発行
- `analytics-service` — GA/AdSense分析
- `platform-service` — バックアップ等の運用系機能
- `log-writer` — ログ収集（既存）

## Consequences

**利点**

- サービスごとに障害が隔離され、一部機能の不具合が他機能の可用性に波及しない
- サービスごとに独立してスケール・デプロイできる
- サービスの責務が明確になり、コードベースの見通しが改善する

**欠点・トレードオフ**

- サービス間通信（同期呼び出し・非同期イベント）の設計・実装コストが新たに発生する
- 分散システム特有の複雑さ（結合テスト、相関ID、分散トレーシング等）に対応する必要がある
- ローカル開発環境で起動するコンテナ数が増え、開発体験のコストが増加する
- 移行作業自体に相応の工数がかかる（本 Epic 全体で対応）

## Alternatives considered

**モジュラーモノリス（却下）**

パッケージ境界を明確にしつつ単一デプロイ単位を維持する案。移行コストは低いが、
デプロイ単位が1つのままであるため障害境界の問題を解決できず、根本課題が残る。
また将来的にサービス分割が必要になった場合、結局同様の分割作業が再度必要になる。
