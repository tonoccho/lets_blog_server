# ADR-0004: サービスごとに MySQL スキーマを分離し、跨ぎ JOIN と FK を禁止する

## Status

Accepted

## Context

[ADR-0001](0001-domain-based-microservices.md) によりサービスをドメイン単位で分割する
ことを決定した。しかし現行の `api` は単一の MySQL データベースを、`projects` を筆頭とする
god-table を介して全ドメインが直接JOINできる形で共有している。

サービスをアプリケーション層で分割しても、データストアが共有されたままでは、
あるサービスの都合でスキーマを変更すると他サービスのクエリが壊れるという結合が残り、
[ADR-0001](0001-domain-based-microservices.md) が目指す障害境界・デプロイ独立性が
データ層で骨抜きになってしまう。

## Decision

サービスごとに独立した MySQL スキーマ（例: `lbs_identity` / `lbs_project` /
`lbs_content` 等）を持たせる。スキーマを跨いだ SQL の JOIN、および外部キー(FK)制約は
禁止する。他サービスが所有するデータが必要な場合は、そのサービスのAPI呼び出し
（同期呼び出しまたは非同期イベント経由の複製）を通じて取得する。

## Consequences

**利点**

- サービスが自スキーマの構造を他サービスに影響を与えずに変更できる（デプロイ独立性の確保）
- データアクセスの責務がサービス境界と一致し、どのサービスがどのデータの正とみなされるかが明確になる
- スキーマレベルでの結合が排除され、[ADR-0001](0001-domain-based-microservices.md) が
  目指す障害隔離が実効性を持つ

**欠点・トレードオフ**

- これまでJOINで一括取得できていたデータを、サービス間のAPI呼び出しやイベント経由の
  複製で組み立て直す必要があり、実装コストと若干のレイテンシ増加が発生する
- 参照整合性をDBのFK制約で保証できなくなるため、整合性維持はアプリケーション層
  （イベント駆動の同期、補正処理等）で担保する必要がある
- god-table (`projects` 等) の分割作業自体に相応の移行コストがかかる

## Alternatives considered

**共有スキーマの維持（却下）**

アプリケーション層のみをサービスに分割し、データベースは既存の単一スキーマ・
god-tableを共有し続ける案。移行コストは最小だが、スキーマレベルの結合が残るため
サービス間の暗黙的な依存が排除できず、[ADR-0001](0001-domain-based-microservices.md)
で意図した独立デプロイ・障害隔離が実現できない。あるサービスのスキーマ変更が
他サービスを壊すリスクが残り続けるため、分割の目的そのものを損なうと判断し却下した。
