# ADR-0005: サービス間通信は Client Credentials によるサービストークン＋元ユーザーIDヘッダーで認証する

## Status

Accepted

## Context

[ADR-0001](0001-domain-based-microservices.md) によりサービスをドメイン単位で分割する
ことを決定した。分割後は、あるサービスが別サービスのAPIを直接HTTPで呼び出すケース
(例: 将来 Phase 19 で分割される publishing→content、analytics→project のような
同期呼び出し)が発生する。これを無認証のまま通すと、内部Dockerネットワークに到達できる
ことだけが実質的な認可条件になってしまい、[ADR-0002](0002-keycloak-oidc.md) が
なりすまし対策として導入したKeycloak検証済みJWTの原則が、サービス間経路では
素通りしてしまう。

サービス間呼び出しを認証する方式として、以下の2案を検討した。

- **案A**: エンドユーザーのBearerトークンをそのまま下流サービスへ転送する
  (下流はユーザー権限で動く)
- **案B**: 呼び出し元サービスが `letsblog-services` クライアント(Client Credentials
  Grant)で取得したサービス用トークンで呼び、元の操作ユーザーIDは別ヘッダーで伝播する
  (下流はサービス権限で動く)

この選択は、監査ログ上でどのアクターとして操作を記録するか(B11: 監査ログのactor記録)
とも整合させる必要がある。

## Decision

**案B(サービストークン＋元ユーザーIDヘッダー)を採用する。**

- サービス間のHTTP呼び出しは、呼び出し元サービスが `letsblog-services` クライアント
  (#559で定義済みのconfidentialクライアント。#562でidentity-service→Keycloak Admin API
  向けに実績あり)のClient Credentials Grantで取得したサービス用アクセストークンを
  `Authorization: Bearer` に載せて呼び出す。
- 元の操作ユーザー(エンドユーザーがいる場合)のIDは、専用ヘッダー(例:
  `X-On-Behalf-Of-User-Id`。実際のヘッダー名・値の形式は、これを実際に使い始める
  Phase 19 の各サービス抽出Issueで確定する)で別途伝播する。呼び出し先サービスは
  サービストークンで認証しつつ、このヘッダーの値を「実際に操作した人物」として
  監査ログ(B11)のactorに記録する。
- 案Aを却下した理由は「Alternatives considered」参照。

サービス用トークンの取得・キャッシュ(有効期限内の再利用)・期限前の自動更新は、
`libs/lbs-common` の `com.letsblog.common.auth.ServiceTokenClient` として共通実装する
(#567)。将来Phase 19で実際のサービス間呼び出しが必要になった時点で、呼び出し元は
このクラスを利用してトークンを取得する。同クラスは、トークンエンドポイントへの
到達不可・エラー応答が連続した場合にサーキットブレーカーを開き、呼び出し元が
毎回タイムアウトいっぱいまで待たされることを防ぐ。

## Consequences

**利点**

- 下流サービスは「どのサービスが呼んだか」をトークンの発行者(`azp`/クライアントID)
  から機械的に判定でき、エンドユーザーのトークンのスコープ・有効期限に引きずられない
- サービス間の認可を、エンドユーザーの認可とは独立に(例: サービスアカウントに
  絞ったロールで)設計できる
- 元ユーザーIDをヘッダーで明示的に伝播するため、監査ログのactor記録(B11)が
  「どのサービス経由で、誰の操作として」実行されたかを両方とも保持できる

**欠点・トレードオフ**

- エンドユーザーの権限とサービストークンの権限が一致するとは限らないため、
  下流サービス側で「サービストークンが伝播してきたユーザーIDに対して本当に
  実行してよい操作か」を再度チェックする実装が必要になる(案Aであれば下流は
  ユーザーのJWTクレームをそのまま信頼できるため、この二重チェックが不要だった)
- 元ユーザーIDヘッダーは呼び出し元サービスの自己申告であり、下流サービスから見て
  「サービストークンさえあれば任意のユーザーIDを騙れる」という新たな信頼境界が生まれる。
  内部ネットワーク上のサービス間限定の経路であるため許容するが、将来的にこの経路が
  外部に露出しないよう、ルーティング・ネットワーク境界の設計で担保する必要がある

## Notes: このIssue(#567)時点での実装範囲

2026-08時点で、実際にサービス間で直接HTTPを呼び合う経路は
`identity-service → Keycloak Admin API`(#562。外部IdP呼び出しであり、ここでの
「サービス間通信」の対象ではない)のみで、`gateway` の各ルート
(`services/gateway/src/main/resources/application.yml`)はいずれも
`publishing`/`content`/`analytics`/`project` 等の分割前で、実体は単一の
`legacy-api` コンテナを指している(Phase 19の各サービス抽出Issueが未着手のため)。
つまり、本ADRが対象とする「ドメインサービス同士の直接HTTP呼び出し」自体が
まだ実在しない。

このため#567では、将来の実際の呼び出しに備えた基盤(`ServiceTokenClient` の
共通実装と本ADR)のみを整備し、以下は次のいずれかの後続Issueに委ねる。

- 実際のサービス間呼び出しの認証を必須化し、無認証呼び出しを401にする実装
  (対象となる呼び出しが実在しない現時点では、`gateway`→`legacy-api`/`identity-service`
  のようなエンドユーザートラフィック転送経路と誤って混同・適用すると、
  現状唯一の実ユーザーアカウントの既存アクセス経路(`X-Actor-Id`ヘッダー方式。
  #566で撤去予定)を壊しかねないため、Phase 19で実際のサービス間呼び出しが
  生まれるタイミングで、その呼び出しにのみ適用する)
- 案Bのヘッダー名・形式の最終確定、および下流サービスでのサービストークン受理・
  元ユーザーID解決の実装
- サービストークンで実行された操作を監査ログ上で識別する実装(既存の`audit_logs`
  テーブルは`user_id`カラムのみで、サービスアクター用の識別子を持たないため、
  実際の呼び出しが生まれた時点でスキーマ変更を含めて設計する)

## Alternatives considered

**案A: エンドユーザーのBearerトークンをそのまま下流サービスへ転送する(却下)**

実装が単純で、下流サービスは既存のOAuth2 Resource Server検証(#563で
legacy-api/identity-serviceに導入済み)をそのまま使い回せる。しかし以下の理由で却下した。

- サービス間の内部呼び出しであっても、実行できる操作がエンドユーザーのトークンの
  スコープ・ロールに完全に縛られてしまい、サービス側の内部処理(例: 集計・後処理)に
  必要な権限をユーザーロールと無関係に設計できない
- エンドユーザートークンの有効期限が、サービス間の非同期的・長時間の処理
  (例: バルク処理、集計バッチ)の実行時間より短い場合、処理途中でトークンが
  失効し呼び出しが失敗しうる。サービストークン(案B)であれば、この失効は
  `ServiceTokenClient` のキャッシュ・自動更新で吸収できる
- 「どのサービスが呼んだか」を判別する手段がトークンのクレームに含まれず、
  下流サービスでのアクセスログ・監査ログ上でサービス起点の呼び出しとエンドユーザー
  起点の直接呼び出しを区別しづらい
